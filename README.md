# WeatherMind

**Hyper-local flood-risk decision support for police, emergency response and municipal teams.**
Chennai · Coimbatore · Erode · Tirupur

Instead of reporting "58 mm of rainfall is expected", WeatherMind answers the questions an
officer actually has: what does this rain mean *for this specific neighbourhood*, how close
is it to a decision threshold, how confident is the model, and what would have to change for
the answer to be different.

---

## Quick start

```bash
python -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python scripts/generate_training_data.py              # writes data/training_data.csv
python scripts/train_model.py                         # optional — the app self-trains
streamlit run app.py
```

Opens on <http://localhost:8501>. No API key required — the decision brief falls back to a
deterministic template built from the same payload, so the demo never depends on a network call.

To enable LLM briefs, copy `.streamlit/secrets.toml.example` to `.streamlit/secrets.toml` and
add `ANTHROPIC_API_KEY` (or `OPENAI_API_KEY`).

Run the test suite:

```bash
python tests/test_pipeline.py        # or: python -m pytest -q
```

## What the pipeline does

```
role + city + area
        ↓
weather inputs (actionable)  +  spatial vulnerability (immutable, frozen)
        ↓
feature engine  →  intensity, effective runoff, drainage deficit
        ↓
Random Forest  →  risk class + tree-vote confidence
        ↓
   ┌────────────┴────────────┐
factor analysis        counterfactual engine
(SHAP / sensitivity)   (actionable features only)
   └────────────┬────────────┘
        ↓
threshold band + risk response surface  →  plausibility filter
        ↓
historical incident retrieval (per area)
        ↓
grounded LLM decision brief
        ↓
officer feedback → logged for recalibration
```

### The three design commitments

**1. Recourse is restricted to forecastable variables.**
`src/counterfactual.py` only ever moves rainfall, duration, wind and antecedent rain.
Elevation, slope, drainage vulnerability, imperviousness and soil infiltration are declared
immutable in `src/config.py` and are frozen everywhere — there is a test
(`test_counterfactuals_never_touch_immutable_features`) that fails the build if that is ever
violated. Telling an officer to improve drainage before tonight's rain is not advice.

**2. Risk is a response surface, not a threshold.**
The threshold band is the range over which the forest moves from 35% to 65% agreement, not a
single cut-off. The 2-D surface tab shows whether the current forecast sits on a flat plateau
or a cliff edge, which is the difference between "a 10 mm forecast error is irrelevant" and
"a 10 mm forecast error flips the decision".

**3. The LLM is last and least trusted.**
It receives a structured payload and is instructed to use nothing else. It cannot overrule the
model's class. You can inspect the exact payload in the UI before every brief.

## Data provenance — read this before presenting

Be straight with judges about where each dataset comes from. It is a strength, not a weakness:
knowing the limits of your own data is the difference between a prototype and a demo.

| File | Provenance | Status |
|---|---|---|
| `data/spatial_vulnerability.csv` | Hand-curated from published flood-risk reporting | Directional values, not surveyed measurements |
| `data/historical_incidents.csv` | Real reported events, transcribed | **Marked `illustrative-verify` — confirm each against its source before the demo** |
| `data/rainfall_baselines.csv` | Approximate per-city rainfall statistics | Replace with IMD / Kaggle-derived percentiles |
| `data/training_data.csv` | Generated by `scripts/generate_training_data.py` | Labels come from an explicit hydrological score, not observed floods |

### Why the training labels are generated

No public dataset labels *neighbourhood-level flood outcomes* for Indian cities. Kaggle's
rainfall datasets give you weather, not consequences. So the training set samples realistic
scenarios per area and labels them with a readable 40-line function
(`src/features.latent_risk_score`) that anyone can inspect and argue with.

That is an honest design choice, and it is the right answer to the question a judge will ask.
The model is a real Random Forest learning real feature interactions; the assumption layer is
visible rather than hidden. Say so directly rather than implying the labels are observed.

### Swapping in real data

* **Real training data** — drop a CSV at `data/kaggle_rainfall.csv` containing the columns in
  `config.FEATURE_ORDER` (minus the derived three, which are computed for you) plus a
  `risk_class` column of 0/1/2. `data_loader.load_training_data()` prefers it automatically.
* **Real rainfall percentiles** — recompute `daily_p90_mm`, `daily_p99_mm`,
  `daily_record_mm` from *Rainfall in India 1901–2015* or *Daily Rainfall Data – India
  (2009–2024)*, and overwrite `data/rainfall_baselines.csv`.
* **Verified incidents** — replace rows in `data/historical_incidents.csv` and change
  `source_status` to the source name. The brief's wording adapts automatically.

Nothing else in the codebase changes in any of these cases.

## Deploying to Streamlit Community Cloud

1. Push this folder to a public GitHub repo (`.gitignore` already excludes secrets, model
   artifacts and logs).
2. On <https://share.streamlit.io>, create an app pointing at `app.py`.
3. Under **App settings → Secrets**, paste the contents of your `secrets.toml`.
4. Deploy. The first request trains the model in a few seconds and caches it, so no build step
   is needed. `data/training_data.csv` is committed, so a cold host works out of the box.

If the free tier struggles with `shap`, remove it from `requirements.txt` — the factor tab
falls back to per-instance sensitivity analysis and the UI states which method produced the
numbers.

## Demo script (about four minutes)

1. Open on **Coimbatore → Peelamedu**, role *Police / Traffic Control*.
2. Set rainfall to ~120 mm over 12 h. Read the risk banner and the confidence line.
3. **Factors tab** — note that blue bars are forecastable and purple bars are terrain, and that
   the purple ones are deliberately off-limits to the engine.
4. **Threshold tab** — show the band, not a number. Point out the headroom figure.
5. Scroll to the rejected counterfactual and explain why the plausibility filter threw it out.
6. **Risk surface tab** — show the dashed 50% boundary and the dotted "beyond anything on
   record" line. Read the plateau-versus-cliff sentence aloud.
7. **What-if tab** — hit *Cloudburst*. Same total, shorter window, different decision.
8. **Decision brief tab** — generate, then open *Exact payload sent to the model* to show the
   LLM invented nothing.
9. **Switch the city dropdown to Chennai → Velachery** without changing anything else. Same
   pipeline, different ground, different answer. This is the proof-of-generalisation moment.
10. **Model card tab** — close on the stated limitations. Owning them lands better than hiding
    them.

## Known limitations

* Training labels are generated, not observed (see above).
* River stage and reservoir release are not modelled, which matters most for Bhavani Riverside
  in Erode and Noyyal Riverside in Tirupur, where the dominant driver is upstream flow rather
  than local rainfall.
* The spatial table is directional, not surveyed.
* The feedback loop captures and schematises officer responses but does not retrain; the
  retraining design is described in the UI rather than implemented.
